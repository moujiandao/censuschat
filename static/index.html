Where the data comes from

Every number this assistant reports is read live from Snowflake, from the US_CENSUS.PUBLIC schema. That database was imported from a Snowflake data share published by SafeGraph — their "Open Census Data" product, which repackages US Census Bureau ACS and decennial releases joined at the census-block-group grain. It is Census-sourced data, redistributed by SafeGraph.

The assistant is pinned to the 2020 vintage, which is the ACS 2016–2020 5-year estimates. Block-group-level ACS is only ever published as a 5-year rolling estimate — the Census Bureau does not release 1-year estimates for populations under roughly 65,000 — so every figure is a five-year average, not a point-in-time count for 2020.

A 2019 vintage (ACS 2015–2019) also exists in the same schema but is deliberately excluded. The 2020 decennial census redrew block-group boundaries, so 2019 and 2020 block groups are not the same physical areas and must never be compared row-to-row. Restricting to one vintage makes that mistake unrepresentable.

Grain: everything is a census block group

There are no state, county, or tract tables in this database. Every demographic, geometry, and metadata table has one row per census block group (CBG), keyed by CENSUS_BLOCK_GROUP — a fixed 12-character string. Any county or state answer is computed by aggregating block groups whose key starts with the right prefix.

Roll-up is string truncation: state = first 2 characters, county = first 5, tract = first 11. Counts are summed; medians and rates cannot be summed and are handled separately, because a median of medians is not a median.

How a variable is named

A column name like B19013e1 is not arbitrary. It decomposes into the ACS table number, an estimate/margin marker, and the field's position within that table.

B19013ACS table number. Its first three characters also select the physical Snowflake table (B19 → 2020_CBG_B19).
eEstimate. The value itself.
mMargin of error — the 90% confidence half-width, stored as a separate column with an identical numeric type. Every estimate has a paired m sibling.
1Field position within the ACS table.

Each variable also carries a universe — the population it is counted against: Total population, Households, Housing units, Workers 16 years and over — 140 distinct universes across the bundle. Two variables from different universes cannot be divided into a meaningful rate. Several hundred block groups have people but zero households (dorms, prisons, barracks), which is exactly where that mistake surfaces.

Local lookup snapshots

Variable search and geography resolution never touch Snowflake. They run against a local SQLite file built ahead of time from the two metadata tables, so discovery is fast and offline. At request time Snowflake is contacted exactly once, by the SQL tool.

Known traps in this data

NULL is not zero Suppressed values are stored as SQL NULL, not a sentinel like −666666666. Median household income is NULL for a few percent of block groups — too few households to estimate reliably. Those are reported as "not reported," never as 0.
Top-coded values A median household income of exactly 250001 means "$250,000 or more," not $250,001. A value sitting exactly at a median column's maximum is usually a top code, not a real median.
Margins of error are separate columns Estimates and margins have the same data type and differ by one character in the column name, so selecting the wrong one is silent.
Universe mismatches Dividing a population count by a household count produces a number that looks fine and means nothing.
Places aren't in the data Cities, ZIP codes, and metro areas have no clean block-group definition here. Questions about "Austin" are answered for Travis County, with the substitution stated, or declined.
