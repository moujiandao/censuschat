### Fixed
- **Critical**: every live `run_census_sql` call was failing with `invalid identifier` — confirmed via `INFORMATION_SCHEMA.COLUMNS` that ACS variable columns are stored case-sensitively (e.g. `B01001e23`), but `SYSTEM_PROMPT`'s own aggregation-pattern example showed an *unquoted* `SUM(<variable_id>)`, teaching the model the wrong pattern: Snowflake folds an unquoted identifier to uppercase, which doesn't match the real column, so every query failed and burned the full bounded-recovery budget (issue #12) before giving an honest failure. Found live in the browser while testing the new frontend — two consecutive real questions ("Wyoming?", "Travis County?") both failed 2-for-2 with recovery exhaustion, despite passing every unit test (the mocked test harness never exercised real Snowflake identifier resolution). Fixed by adding an explicit, highest-priority correctness rule ("every variable_id column reference MUST be double-quoted") and quoting the aggregation-pattern example itself. **Verified live**: both previously-failing questions now return correct grounded answers (Wyoming 581,348; Travis County, TX 1,250,884), and a follow-up ("what about Travis County, Texas?") correctly resolved via session context. This was a real, unmocked-only-catchable regression — a reminder that this project's mocked test suite (rule 19) cannot catch prompt-quality bugs that only manifest against the real database's actual identifier casing
