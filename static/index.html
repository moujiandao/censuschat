censuschat

Ask about US population, income, or housing from the 2020 ACS 5-year estimates.

Example questions

Question → Guardrail → Local discovery → SQL gate → Snowflake → Normalize → Answer → Evidence

Code protections

SQL is parsed as one SELECT-only Snowflake statement, checked against a table allowlist, given a LIMIT, and run with a statement timeout. User text is never interpolated into SQL.

Model instructions

The model is instructed to ground answer numbers in this turn's query results. The serving path does not independently validate every final answer number.

Evaluation checks

Six stable scenarios are regression and eight broader scenarios are capability. Each result is pass, fail, or inconclusive.

Three tools, two data locations

  • search_census_variables searches a local SQLite FTS snapshot.
  • resolve_geography ranks local SQLite geography records.
  • run_census_sql is the only request-time path to Snowflake, and every query crosses the SQL gate.

Source, grain, and vintage

The allowed Snowflake tables come from SafeGraph's Open Census Data share and repackage US Census Bureau data. This app is pinned to the 2020 vintage, the ACS 2016-2020 5-year estimates, at census-block-group grain. State and county counts are computed by aggregating block groups. The local discovery snapshot contains labels and geography identifiers, not answer values.

Design Trade-Offs

Why Census Chat works this way: the problem behind each decision, an example to remember it by, and what we gained or gave up. These are lessons from this build, not rules that every app must follow.

1. Who should write the database query?

In your app: agent_turn (src/agent.py) asks the model for tool calls. The model sends SQL to run_census_sql (src/tools.py), which calls validate_sql (src/sqlgate.py) before executing the accepted query in Snowflake.

The problem: Snowflake needs precise SQL instructions. The model can understand a question about employment and still write a query with the wrong quotation marks or an invented table name.

DesignStrengthCost
LLM writes SQL, code validates it The model writes the whole query, so it can combine data in ways we did not build a specific template for. Code must check its work. A query can be rejected and need another attempt before the user gets an answer.
LLM selects options, code builds SQL The model picks a metric, location, and supported calculation. Tested code assembles the query with the correct syntax and verified table names. We must build each supported calculation. A request outside that menu needs more implementation.

Example: for an employment total in Texas, the model could write the entire SQL statement, or select “employment count + Texas + total” and let code write it. The second path removes syntax choices, but the model could still select the wrong employment measure.

Remember: writing freely gives flexibility; choosing from a tested menu gives predictability. Today the model writes SQL and code validates it. The menu approach is an option to evaluate, not a shipped feature.

2. Asking the model to follow a rule is not enforcing it

In your app: validate_sql checks query structure and ALLOWED_TABLES. Separately, agent_turn blocks SQL when resolve_geography reports unresolved ambiguity. Multiple matches for “Washington County” trigger clarification instead of a silent choice.

The problem: a prompt saying “only read approved tables” is an instruction the model can get wrong. We need the app to stop a forbidden query even when the model tries it.

Our choice: code checks SQL before Snowflake sees it and rejects queries that violate the rules. For example, an instruction to delete records is blocked even if the model generated it. Code also controls retry limits and time budgets.

Remember: the prompt explains the rules; code controls what can happen. The cost is writing and maintaining those checks, and sometimes rejecting a query the checker cannot safely understand.

Decision record: D-007, D-010, D-013, D-014. The gate checks query structure; passing it does not prove the answer is statistically correct. Row limits, explicit columns, and execution timeouts bound different resources.

3. Let the model look up data instead of memorizing a short list

In your app: search_census_variables answers “which measure?”; resolve_geography answers “which place?” Both live in src/tools.py and read the local SQLite snapshot prepared by build_snapshot (src/snapshot.py). For rented homes in Travis County, the first finds the renter measure and the second finds the county’s geographic code. Neither retrieves the final count: that is run_census_sql’s job.

The problem: Census has thousands of measures. Putting a handful of familiar ones in the prompt would make population demos easy, but could miss a less expected question about housing or commuting.

Our choice: the model searches a local copy of the catalog when a question arrives. For “How many homes are rented?”, it looks up available measures before choosing what to query.

Remember: give the model a searchable catalog, not just a cheat sheet. This expands discovery, but introduces search errors and a local catalog that must be kept current.

Architecture §2-4: local SQLite lookups keep discovery fast and avoid warehouse calls. The trade-off is maintaining a snapshot that must be rebuilt when the catalog changes.

4. A successful retry can hide a recurring bug

In your app: agent_turn (src/agent.py) returns tool errors to the model and tracks recovery_attempts and recovery_log. The Evidence tab exposes failed and successful tool calls so you can inspect the repair sequence.

What happened: the model generated incorrectly quoted column names, received a database error, and sometimes fixed the query on retry. The user got an answer, making the system look healthier than its first attempt really was.

The trade-off: recovery saves a conversation, but costs extra time and model calls. If we only count final success, we can miss the same avoidable mistake happening repeatedly.

Remember: “worked immediately,” “worked after repair,” and “failed” are different outcomes. Track them separately so recovery does not become an excuse to leave the original bug unfixed.

Source: Reflection §4, the quoted-identifier incident. This is a measurement lesson, not a claim that every metric is already implemented.

5. Testing the parts and testing the real answer are different jobs

In your app: tests/test_sqlgate.py checks validate_sql offline; tests/test_agent.py checks loop controls with simulated responses. evals/scenarios.py defines live cases, and evals/run_evals.py runs and scores them through the real agent_turn.

Offline example: give the SQL validator a saved DELETE statement or a query against a disallowed table. Check that it rejects the query before contacting Snowflake. This is fast, repeatable, and needs no paid model call.

Live example: ask the original employment question again using the real model and Snowflake. Check whether it picks the right data and returns the expected answer. Its newly generated query can differ on each run.

Remember: offline tests check predictable code behavior; live evals check whether the full app delivers. Live runs cost more and can vary, while offline tests cannot prove that the real model and database work together.

Reflection §4: calibrate graders against known-correct and deliberately wrong answers. A failing score can reveal a broken grader; a passing score only supports what the checks actually measure.

6. A plausible number is not always an answer we can support

In your app: ALLOWED_TABLES (src/contracts.py) enforces the permitted vintage through validate_sql. In src/tools.py, resolve_geography searches available places and _geo_levels_for marks median measures as valid only at block-group level. That metadata informs the model; it is not itself a SQL-level ban on averaging medians.

Example: a user asks about Austin, but our source does not include city boundaries. Returning Travis County's population as Austin's population would sound convincing and still answer the wrong question.

Our choice: explain missing coverage and make any substitute explicit. We also restrict queries to the 2020 ACS release. For income, averaging neighborhood medians does not produce the county median, so that shortcut is not a valid substitute.

Remember: fewer supported questions is an accepted cost of being honest about the data. Expanding coverage requires the right data and calculations, not just a more confident prompt.

Decision record: D-002, D-003, D-005, D-009. A county substitute or a mean instead of a median must be explained. The single-vintage restriction avoids boundary and overlapping-window complications; it is not a claim that every comparison across years is invalid.

7. Search can be so strict that it misses data we have

In your app: search_census_variables uses SQLite FTS5 keyword search and BM25 ranking. Its helper _fts_match_query builds the strict AND search, then an OR search if no rows match. _should_index_variable (src/snapshot.py) excludes margin-of-error and allocation fields when building the index.

What happened: searches like “number of households” returned nothing because all words had to appear together in a Census label. The household data existed, but the wording did not match.

Our choice: try the strict search first. If it finds nothing, try matching any of the words. Local keyword search keeps the setup simple, without a separate service for matching by meaning.

Remember: broader search finds more possibilities but also more distractions. “Number of households” can surface “number of rooms,” so the model must still check what a result means. We also exclude margins of error from normal search to reduce misleading matches.

Decision record: D-008, D-020. Search relevance still needs evaluation; finding a variable does not establish that it is the right one.

8. If the topic checker breaks, should chat stop?

In your app: classify_input (src/guardrail.py) calls the classifier and allows requests on errors or timeouts. _ALLOW_VERDICTS includes unknown_subject. Later, run_census_sql raises SqlRejected if validate_sql rejects the query, before opening a Snowflake connection.

The problem: a small model first checks whether a question belongs in Census Chat. If that check times out while someone asks a legitimate population question, refusing everything would make a helper component take down the experience.

Our choice: let the question continue when the topic check fails. The SQL gate still runs and blocks queries that fail validation. A question about an unknown place also gets a chance to reach data discovery.

Remember: losing the topic checker may waste an extra model call; losing SQL validation must stop execution. The two checks have different consequences, so their failure behavior is different.

Reflection §1; decision record D-019. The classifier helps route requests efficiently; it is not the SQL security boundary.

9. How long should the agent keep trying?

In your app: agent_turn counts failed or empty SQL results against MAX_RECOVERY_RETRIES, limits rounds with _MAX_TOOL_LOOP_ITERATIONS, and checks elapsed time before further work. Separately, run_census_sql sets Snowflake’s STATEMENT_TIMEOUT_IN_SECONDS to limit query execution.

Example: the model cannot find household data, searches again, rewrites the query, and searches again. Without limits, one question can keep consuming time and paid calls without making progress.

Our choice: cap recovery attempts and tool rounds, and stop further tool use when the time budget is exhausted. Explain the failure instead of endlessly retrying.

Remember: more attempts can rescue difficult questions, but also make failures slower and more expensive. Fix why the agent is stuck before simply giving it a larger budget.

Decision record: D-013, D-020. Successful recovery is useful evidence, but should remain distinguishable from first-attempt success.

10. Keep a useful activity log without building a monitoring platform

In your app: TraceSpan records each step and TurnTrace groups a turn (src/tracing.py). record_turn_trace saves it to SQLite; get_traces retrieves it. /api/traces feeds the history displayed by the Evidence tab.

The need: when an answer fails, we need to see which searches and queries ran, what failed, and how long each step took. The in-app trace view provides that record.

Our choice: defer Langfuse, a separate monitoring service, to fit the build budget. Store traces locally in SQLite so deploying a new version does not erase the old evidence.

Remember: this helps explain one conversation, but does not provide shared monitoring across several servers or automatic alerts. It is simpler to operate today; a larger service would need more monitoring and a policy for deleting old history.

Decision record: D-021, superseded for persistence by D-023. Earlier reflection text describing memory-only traces is historical.

11. “Connected at startup” does not mean “connected right now”

In your app: lifespan (src/app.py) calls check_snowflake_reachability at startup. In src/health.py, health_report and is_degraded read the cached result. The browser’s /api/health request does not perform a new Snowflake connection test.

Our choice: test the Snowflake connection when the app starts and remember the result. Reading that saved status is cheaper than opening another database connection on every health check.

Example: if Snowflake becomes unavailable an hour later, the saved status may still say healthy. The next real query will expose the problem, but the saved check cannot warn us first.

Remember: this was enough for checking a fresh deployment. Continuous outage detection would need refreshed checks, with the extra work and connections that brings.

Decision record: D-015; implemented in the health module.

12. Use a simple setup that fits the server we already have

In your app: src/app.py serves static/index.html directly. Its activateTab function switches visible panels. deploy.sh starts the app container, and docker-compose.override.yml publishes it on 127.0.0.1:8000 for the host’s Caddy server.

Our choice: keep the frontend in one HTML file, with no separate build process. Reuse Caddy, the server already handling HTTPS and login protection, instead of starting a competing copy that would disrupt another site.

Example: adding this learning tab only needs an HTML edit. But moving the whole app to another machine also requires recreating the existing server configuration; the container alone does not describe everything.

Remember: fewer moving parts helped us ship. The cost is a growing frontend file, manually maintained explanation pages, and some setup tied to this host.

Decision record: D-016, D-017. Simplicity was chosen for this deployment and build budget, not as a universal architecture rule.

13. A long test list can look more convincing than it is

In your app: evals/scenarios.py holds the active scenarios. evals/run_evals.py writes results into evals/results/. The /api/evals endpoint (src/app.py) supplies recorded results to the Evals tab; opening the tab does not run evaluations.

What happened: the evaluation page mixed executed scenarios with a much larger backlog of scenarios that had never run. Readers had to work too hard to understand what was actually verified.

Our choice: reduce the active set, preserve historical results, and label the captured but unrun regression as pending. The report is easier to read, but omitted coverage still needs work.

Remember: a written test idea is not evidence. A smaller executed set is easier to assess, but cannot justify claims about cases it never tested. Keep gaps visible and preserve failures.

Decision record: D-022. Never erase failed results to improve the reported score.

14. Build one complete answer early enough to learn from it

In your app: The form in static/index.html posts to /api/chat. agent_turn coordinates search_census_variables, resolve_geography, and run_census_sql, then streams events back to the browser. Exercising that whole path checks how the parts work together.

What helped: inspecting the real data before coding uncovered missing city boundaries and invalid ways to combine medians. That prevented us from planning features the dataset could not support.

What hurt: the browser interface came late. Offline tests passed, but typing real questions exposed database naming problems that simulated database responses could not catch.

Remember: investigate the data, then get one question working from browser to database to answer. Planning reduces bad assumptions; using the complete app reveals the assumptions you still missed.

Reflection §1, §2, §4. Planning and isolated tests cannot substitute for exercising the complete user journey.
