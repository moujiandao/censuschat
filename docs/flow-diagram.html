Phase 1 - Boot: where the local SQLite comes from

once at startup

It is built from Snowflake, then never touched again

build_snapshot() runs two developer-authored SELECTs against Snowflake's metadata tables and writes the results to data/snapshot.sqlite3.

This is the one deliberate exception to the "Snowflake only via run_census_sql" rule - that rule scopes to request time. No user text ever reaches these two queries.

metadata only

It holds names, not numbers

Zero demographic values live in the snapshot. It is a catalog of what exists, so the model can look up an ID instead of guessing one.

durability

Written atomically

Built into a temp file and rename()d into place, so a crash mid-build never leaves a half-written snapshot for the next boot to read.

The snapshot_meta table is written last - its presence is what marks the file as a complete build.

Phase 2 - The two local tools

They resolve names, they don't fetch data

Neither tool returns a subset of the census data. They translate English into identifiers that the eventual SQL needs:

InputOutput
"median household income"B19013e1
"Travis County, Texas"48453

Why "scanning everything" isn't a concern

The whole file is 2.7 MB and lives on local disk. search_census_variables uses FTS5 with BM25 ranking and returns LIMIT 10; resolve_geography is an equality match on indexed columns. Both are single-digit milliseconds with no network.

Variable IDs are reached at runtime rather than listed in the prompt - with thousands of them, a prompt-embedded list would let the model pattern-match a plausible ID that does not exist.

Ordering

Resolve first (local, free, fast), query last (remote, slow, metered). Nothing hardcodes this - the model chooses each round - but it falls out of the fact that run_census_sql has nothing to put in a query until the other two have run.

Phase 3 - What actually limits the Snowflake scan

gate

validate_sql validates; it does not sanitize

Sanitizing means cleaning dangerous input and hoping you covered every case. This parses the statement into an AST with sqlglot and proves it matches a small set of permitted shapes, rejecting everything else.

If sqlglot cannot model a construct, that is a rejection - an expression the gate cannot inspect is one it cannot vouch for.

7 checks, in order

What it enforces

parses cleanly | exactly one statement | no opaque commands (CALL, EXECUTE) | is genuinely a query | no banned constructs (INTO, session vars, SELECT *) | every table on the allowlist | bounded by LIMIT 200.

The only thing it modifies is the row limit: injected when absent, clamped when too large.

Three independent scan limits

1. the WHERE SUBSTR(...) clause narrows to one geography's block groups. 2. the mandatory LIMIT 200. 3. the SELECT * ban (D-007) - those tables average ~280 columns, so a star under LIMIT 200 still pulls ~56,000 cells into context.

Phase 4 - The four code-enforced stops

Bounded recovery - 2 attempts

A failed or zero-row run_census_sql spends the turn's budget. Once spent, the loop stops asking the model and emits an honest failure naming exactly what was tried.

Ambiguity block

If resolve_geography returned ambiguous=true and the model tries to query anyway, Snowflake is never touched - the turn is force-terminated with a clarifying question listing every candidate.

50-second watchdog

Checked at round boundaries only, never mid-call: a query already in flight finishes and its rows are kept. Only the next round is prevented.

The partial answer is assembled from rows this turn's queries actually returned (capped at 50). The model is never asked to summarize - that would spend the budget that just ran out and risks narrating an ungrounded number.

8-round loop cap

An infrastructure backstop against a runaway loop, independent of the recovery budget.

Why the boundary is drawn where it is

Everything above validate_sql - the system prompt's correctness rules, the Haiku guardrail - is advisory. A model can be argued out of an instruction; a classifier can be fed a phrasing it misreads.

Neither can be argued out of a pure function that parses your SQL and returns ok=False. Put the security in the layer that cannot be talked to; use the soft layers to reduce how often you reach it.

fails open

The guardrail deliberately allows on failure

On a Haiku timeout (1.5 s) or error, the verdict is ALLOW. A classifier outage must never block a legitimate question. The tradeoff is safe precisely because the SQL gate is still downstream.

Its job is cost, not security: refusing at the guardrail costs one small call instead of a full Sonnet tool loop.

label design

unknown_subject exists because of a real bug

"Population of Atlantis?" is shaped like a census question. The classifier was labeling it off_topic and refusing, when the right behavior is to let the tools look and report honestly that it isn't there.
