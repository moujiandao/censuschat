### Added
- **Run history in the Evals tab: a scenario × commit grid, so "are we improving?" is answerable without Langfuse.** `evals/results/` was already a version history (every run writes a timestamped file carrying `run_at`, `git_sha`, `pass_rate` and every per-scenario result), but `/api/evals` read only the newest two files and threw the rest away. It now returns a compact `history` projection of every recorded run — `{run_at, git_sha, pass_rate, scenarios: {id: passed}}`, deliberately not the full runs, since the grid only needs pass/fail per cell. `latest.json` is skipped when building it because it is a copy of the newest timestamped file, and counting it twice would show a phantom extra column on the one view whose job is measuring change. New `_history()` in `src/app.py`; `previous` is gone from the response since nothing rendered it.
- **`--repeat N` on the eval runner, because one run is not a measurement.** With a live model a scenario is a coin with an unknown bias — `PM-08` passes roughly two runs in three — so a single run reports flake as a clean pass or a clean fail, and a one-row delta on a 14-row set sits inside the noise. `--repeat` runs the whole set N times and writes **N separate result files** rather than aggregating: N passes are N independent measurements, and keeping them as separate `EvalRun`s means flake becomes visible with **no change to the frozen contract** (rule 12 untouched — there was no field to put "2 of 3" in, and now none is needed). `main()` split into `_run_all()` (one scored pass) and `_write()`, which now also guards against two runs in the same second overwriting each other, since silently discarding a measurement is the one failure a repeat run exists to prevent.
- Render the grid in `static/index.html`: one column per commit, oldest first, `✓` passed, `✗` failed, `·` not in that run, and `2/3` for a commit run several times, with flake styled as its own state rather than folded into pass or fail. A delta line under it reports **fixes, regressions and additions as three separate counts**. That separation is the point: the two oldest recorded runs are 100% and the newest is 93%, which reads as a regression and is not one — the set grew from 11 examples to 14 and one addition is deliberately red. An aggregate pass rate is only comparable across runs whose denominator didn't change, so the grid compares rows and the tab now says so. **Verified live in a real browser** against both the real results (`b61ea07 ×2` collapsing correctly, delta reading "3 added" rather than a regression) and a synthetic three-run commit exercising all four cell states: stable `3/3` green, flaky `1/3` amber, regressed `0/3` red with the delta naming it, and absent `·` correctly counting as neither. 6 tests in `tests/test_app.py` covering the projection, oldest-first ordering, the `latest.json` double-count guard, pending-row exclusion, and survival of a corrupt result file. ### Fixed
- **The guardrail was hard-refusing questions it should have answered honestly (D-019, issue #25).** Reproduced live against real Anthropic + Snowflake: "What's the population of Atlantis?" came back in 1.5s with zero tool calls and the canned "I can only help with questions about US Census demographic data" — a scope rejection for a question that was in scope. The classifier's own `reason` fields showed it already knew the difference and the routing threw it away: Atlantis → `off_topic`, *"a mythical location and not a real US geography that Census Bureau covers"* (a **coverage** judgment) vs weather → `off_topic`, *"a weather question unrelated to Census demographics"* (a **topic** judgment). One label, two jobs, one hard refusal — so the coverage case never reached the tool loop where the honest not-found paths already exist. Split into a second classifier label `unknown_subject` routed to ALLOW; enforcement stays in the routing dict in code, exactly where CLAUDE.md rule 5 puts it, and `RefusalCategory`/`GuardrailAction` are untouched so rule 12's freeze isn't involved. Rejected a code-side "is this demographic-shaped?" heuristic — it relocates the same semantic guess to a worse guesser and would be most brittle on the very inputs it exists to catch. Also added an explicit `_ALLOW_VERDICTS` set: previously any label absent from `_REFUSAL_VERDICTS` fell through to ALLOW, so a new refusal category could be added to the output schema and silently never enforced; every schema label must now sit in exactly one set, pinned by `test_every_schema_verdict_has_explicit_routing`. Rule 6 fail-open still holds for an unrecognized label but now carries `reason="unrecognized_verdict"` so drift shows up in the guardrail span instead of passing as a clean allow. Cost accepted: a fictional/non-US place now costs a ~5s agent turn instead of a 1.5s refusal, bounded by the existing round cap and watchdog. **Verified live**: OT-01 (weather) and INJ-02 (prompt extraction) both still refuse; Atlantis now answers *"There's no place called 'Atlantis' in this data — I only have state and county boundaries available…"*
- **FTS retrieval returned nothing for reasonable queries (D-020).** `docs/reflection.md` ranked this defect first among unfixed issues and guessed the cause was the model "taking too many exploratory calls." It wasn't. `_fts_match_query` ANDed every token, so the live agent got **0 hits on 7 consecutive searches** — "number of households", "total households B11001", "households total count" — and died on the tool-round cap while `B11001`/`B11012` sat in the snapshot. The tokens all existed individually ("number" 54 docs, "of" 1734, "households" 805); their conjunction was empty. AND looked free originally because the Appendix A probe drew queries from in-corpus vocabulary, where real agent queries carry framing words and guessed table ids that Census labels never contain (`variable_id` is `UNINDEXED`, so "total households B11001" can never match by id at all). Fix is strictly additive — try AND, and only on zero rows retry with OR. Measured on the real snapshot: every query where AND matched returned an **identical top-3 in the same order** under OR, empirically refuting the original docstring's "OR would rank a single-rare-term match above the true multi-term hit"; AND-first is kept anyway since it costs nothing and is the validated path. Known imperfection accepted: OR does rank badly for some queries ("number of households" surfaces *Median Number Of Rooms*, since "number" is rare and BM25 rewards it) — still a large improvement, because a mediocre ranked list is something the model can refine against where an empty result gives it no signal and costs a whole round
